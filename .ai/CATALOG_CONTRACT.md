# Kiwa automatic catalog ingestion contract

Date: 2026-10-05 JST. Scope: user-requested automatic collection of the public Kiwa product list into a locally browsable parts library. This contract adds a **catalog candidate** layer; the existing calibrated Part and save contracts remain authoritative.

## Objective and boundaries

- Collect the public `all-item` collection through the provider-documented paginated `/collections/all-item/products.json?limit=250&page=N` endpoint, and persist searchable candidates without Supabase credentials. The operator starts collection once, can pause/resume it, and can inspect progress and failures while browsing collected products.
- A collected candidate is useful catalog information, not an editor-ready Part. Keep separate identifiers, storage, UI labels, and counts. Never insert fabricated Part/image geometry simply to make the catalog appear populated.
- Promotion uses the existing explicit registration, image calibration, CP/Hole definition, validation, AssetService and Part successor flow. With no cloud configuration, browsing and collecting work locally; promotion explains that configured Part storage is required. This scope does not replace all cloud design/Part persistence with a new offline editor.
- No login/cart/customer crawling, headless anti-bot bypass, invented dimensions, hidden API reverse engineering, or deployment/shared-host operating mode.

## Existing evidence

`src/server/kiwaParser.ts` returns `ImportedPartCandidate`; its `success` flag only means selected metadata fields were found. It does not certify geometry. `src/server/publicResource.ts` enforces HTTPS, Kiwa HTML host restrictions, public DNS addresses pinned into each request, redirect validation, a total deadline, content types and size limits. Existing import routes require Supabase auth; `/parts` currently loads authenticated calibrated Parts only. Preserve those protections and cloud behavior.

Live discovery reported by the parent: robots permits public collection/product retrieval, and provider `agents.md` documents read-only collection JSON. Inspected `.ai/evidence/catalog/products-page1.json`: 250 products with stable IDs, handles, variants, SKU, price, option names/values, tags and images. Preserve robots/agents responses with this evidence before full ingestion. The page-1 sample alone does not establish full coverage or a stable snapshot of a changing collection.

## Interfaces and local persistence

- Add a catalog repository separate from `SupabasePartRepository`. Store candidates, job/checkpoint, snapshots and image cache beneath fixed `.local/catalog/`, excluded from source artifacts. No path supplied by a browser may select a filesystem location.
- Durable writes are atomic and schema-versioned. A single-writer lock protects worker/control changes; interrupted writes retain the last valid checkpoint. A second worker must refuse the same catalog. Recover abandoned `in_progress` queue entries to pending on controlled restart. Report corrupt state rather than silently resetting it.
- Candidate identity is provider + published product ID; variant identity is provider + product ID + variant ID. Keep IDs losslessly, retain handle/source URL as metadata and preserve distinct variants even when SKUs overlap. SKU is secondary metadata, not an unconditional uniqueness key. A changed handle does not duplicate a stable product; an absent ID is a visible parse failure rather than a guessed identity.
- Keep original/final source URL, fetch timestamp, parser version, published title/SKU, price and currency, package/dimension option text, categories/tags, image URLs, variant availability, status/error and bounded source snapshot/hash. Preserve unknowns and the last successful snapshot when refresh fails. Price remains per published sale unit; do not derive per-piece price from ambiguous package text. Collection JSON price lacks a currency field in the inspected sample: use JPY only with separately retained storefront currency evidence, otherwise unknown. HTML descriptions are displayed as sanitized text, never injected raw.
- Serve paginated local query/detail/status responses, and start/pause/resume controls. Local catalog does not require Supabase bearer tokens. Its mutation endpoints are enabled only in explicit local mode, require loopback access plus validated Host/Origin and a non-guessable same-session control token, reject cross-site requests and never expose arbitrary URL/fetch/command endpoints. Binding a public host is unsupported and must fail closed. Existing authenticated cloud imports retain auth.

## Discovery and network policy

1. Before source requests, fetch/validate robots and the provider's documented agent policy using a declared crawler user agent. Read `all-item` JSON pages in ascending order starting at page 1. Robots unavailable/malformed or an applicable disallow yields a visible policy halt; no bypass or guessed alternate endpoint. A verified absent robots file may be handled as absent policy, recorded explicitly.
2. Add bounded plain-text/JSON handling for policy and the documented collection endpoint with the same public-address/redirect/deadline/size protections. Reject invalid JSON/schema or a repeated full page with no new IDs as a visible halt. Only fixed approved Kiwa origins/endpoint shapes enter collection requests; no general site crawl. CDNs for images use the existing image resource validation, with separate policy/provenance.
3. One remote request in flight by default, including discovery and images, with at least 1 second between requests or a longer published crawl delay. Persist pacing across worker iterations. Pause and halt stop all new remote requests; in-flight requests may finish and commit safely. No automatic retry loop.
4. Non-success HTTP responses or network/security/content-limit failures halt the job with URL, phase, error and available HTTP status/Retry-After. Persist successes first. Explicit resume is possible after the condition is addressed, observes Retry-After, rechecks policy and does not discard failures. Do not turn 403/429/5xx into ordinary successful completion. Any page cap or resource budget reached yields `limited`, never `complete`.
5. Atomically commit every validated page and its next-page checkpoint together. Crash before commit refetches that page safely; crash after commit resumes at the next page. Start establishes a persisted job; background work runs in a supervised Node worker with durable checkpoints, not an unawaited request promise. Closing the page does not erase progress; stopping the Node worker produces resumable work. This local deployment does not promise serverless background execution.

## Parsing, images and refresh

- Add collection JSON parsing only for fields supported by observed Kiwa fixtures; retain existing HTML import parser for manual/source refresh. Schema recognition must distinguish real product responses from error/anti-bot payloads. Parse failure stays visible, cannot produce a fake successful candidate, and is distinct from transport success.
- Snapshot `success`/`partial` is separate from readiness. Display raw dimensions/package text and unknown structured fields. Do not infer mm/px, alpha masks, CP positions, through holes, shape, mechanical clearance, path segments or calibration from listing photographs or names.
- Cache original catalog images or thumbnails through validated bounded image download/decoding; they remain uncalibrated catalog media. Fetch lazily/on selection if full-catalog image downloading would dominate initial collection. Missing/bad image is a visible placeholder. Image readiness must not be a prerequisite for metadata discovery completeness; separate counts show metadata and cached images. Do not serve arbitrary HTML/SVG or expose raw external-resource proxy URLs.
- Recollection is idempotent. Default resume fetches pending entries; explicit refresh creates new source snapshots and updates catalog metadata only. Existing calibrated Parts, their assets and references never mutate because the provider changed price/image text. A user may review changes through the existing source-refresh/registration workflow.

## Library behavior and completeness

- `/parts` links to `/parts/catalog`, a clearly labeled candidate catalog distinct from registered Parts, searchable by name/SKU/category and known published metadata. Missing numeric fields do not pass numeric range filters. Catalog detail links to the provider, shows fetched-at/provenance/unknowns, and offers variant selection followed by `/parts/new?catalogId=...&variantId=...`. The registration form prefills published fields and loads the original candidate image through the validated same-origin cache; image calibration and Part save remain explicit.
- Progress reports discovery pages, discovered unique products, fetched/partial/failed/pending products, cached images, phase, last checkpoint, halt reason, and whether discovery exhausted or was limited. Keep ingestion status visible without requiring login.
- `complete` means the permitted `all-item` enumeration reached a valid terminal page (fewer than 250 entries, or a subsequent empty page), with no failed page or imposed truncation. Partial metadata is counted separately. “All Kiwa products” is allowed only when authoritative scope/count evidence reconciles with collected distinct product/variant IDs; otherwise display “all-item public catalog” with its scope and collection interval. Products can move between pages while the provider changes its catalog: dedupe IDs, preserve interval, and do not certify a point-in-time complete snapshot from pagination alone. Refresh cannot remove existing entries merely because a product was not observed during a partial run.

## Acceptance and verification

1. With `.env.local` absent, locally start/pause/resume collection, browse/search persisted candidates, restart app/worker and recover the same catalog. Cloud pages retain their existing behavior.
2. Fixtures cover multipage JSON, 250/short/empty terminal pages, repeated pages, duplicate IDs, true variants, handle changes, missing fields, invalid payloads and changed source snapshots. Idempotent rerun does not inflate products or overwrite calibrated Parts.
3. Crash between discovery/fetch/checkpoint writes, stale lease and concurrent start preserve valid state and one worker. A page reload does not spawn duplicate jobs.
4. Robots denial/unavailable policy, 403/429/5xx, retry delay, DNS/private-address/redirect rejection, oversized XML/HTML/image and invalid content halt or reject as specified. Local controls reject cross-origin/non-loopback/arbitrary-input abuse.
5. Live bounded smoke records exact discovery sources, HTTP outcomes and product examples before the full run. Full run records frontier/counts/halts and limits; report actual collection separately from tests. Do not require an unreachable website to pass a fixture suite, or present fixture counts as live ingestion.
6. Targeted tests, typecheck/build, and browser checks prove candidate search/progress/promotion boundary. One bounded independent Sol review is appropriate for local endpoint security, queue/durable-write integrity and the calibrated-Part boundary after implementation; additional reviews need a blocking finding or materially new question.
